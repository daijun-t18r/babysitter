## Problem Statement

凌晨三点,宝宝哭个不停,家长单手抱娃、睡眠剥夺、濒临崩溃。现有选项全部失效:Google 和 ChatGPT 给出无法信任的、不知道宝宝背景的通用长文;打电话给家人有心理成本;记录类 App(Huckleberry 等)在危机时刻毫无帮助。家长需要的是一个**随时可以「拨通」的、了解自己宝宝的、值得信任的深夜声音**——先照顾家长的情绪,再解决宝宝的问题,并在真正危险的时刻明确说「现在就打电话给医生」。

创始人自述(D2):「I am/was that parent」——本人经历过这个时刻,是第一用户。

## Demand Evidence

- 创始人亲历:最糟的夜晚里依次尝试过 Google/ChatGPT 单手搜索、打电话给家人、干扛+刷手机、翻育儿书/App——全部体验过失效(D3 全选)。
- 行业数据:71% 的父母已经在用大模型问育儿问题([AAU 研究](https://www.aau.edu/research-scholarship/featured-research-topics/study-finds-parents-relying-chatgpt-health-guidance));「ChatGPT 是新的婴儿睡眠教练」已成媒体叙事([Salon](https://www.salon.com/2025/09/20/chatgpt-is-the-new-baby-sleep-coach/))。**行为已存在,产品是改良这个动作,不是发明新动作。**
- 缺口(风险):除创始人及伴侣外,尚无能叫出名字的外部用户。见 The Assignment。

## Status Quo(现状及其成本)

ChatGPT 在 3am 场景的具体失效点(D4,创始人亲历):
1. **每次都要重新输入背景**——宝宝几个月大、怎么喂养,每次从零说起;
2. **不敢信**——「best practice 不一定对」,答案对错无从判断,堪萨斯研究显示父母甚至会过度信任错误的 AI 回答;
3. **语气冰冷**——「我快撑不住了」的时刻得到的是百科式回复;
4. **没有场景数据**——「如果 App 知道上次喂奶是什么时候,建议会有用得多」(创始人原话大意)。

注意:创始人**没有**勾选「回答太长」——长度不是核心痛点,信任、上下文、语气才是。

## Target User & Narrowest Wedge

- **第一用户:** 创始人本人 + 伴侣(同一家庭,n=2,验证力有限——已列入作业)。
- **目标画像:** 0-12 个月婴儿的家长,深夜独自面对哭闹/喂养/睡眠/低烧场景,手机是唯一工具,单手操作。
- **Narrowest wedge:** 「深夜拨通的那一个电话」——语音优先的危机对话,三层差异化(均为 ChatGPT 结构性做不到):
  1. **信任:** 临床审核的知识包 + 确定性红旗分诊 + 一键拨号升级 UI;
  2. **上下文:** 月龄 + 喂养方式 + **今晚发生了什么**(被动记忆);
  3. **陪伴:** 夜班护士语气 + SOS 家长冷静模式(「把宝宝放进婴儿床走开是安全的」)。

## Constraints

- 技术栈锁定:Next.js PWA(移动优先)+ FastAPI(全部 AI 与安全逻辑)+ Supabase(auth/Postgres/RLS)+ Claude API(claude-sonnet-5)。
- 语音层:**Vapi**(创始人已有 haus-companion 语音项目经验可复用;Vapi 承担 STT/TTS/打断/实时管线)。
- 单人 + Claude Code 开发;英文市场先行(中文支持为 open question)。
- 医疗敏感领域:上线前必须有儿科临床人员审核分诊规则与知识包(launch gate,不可妥协)。
- **数据治理(健康相关的未成年人数据):** 事件时间轴存储婴儿症状/喂养史,属健康相邻数据。上线前必须定义:保留期限、用户删除机制(GDPR Art.17 / CCPA 删除权,账号删除即级联删除全部数据)、以及是否触发更高合规要求(无医疗机构关系,大概率不构成 HIPAA PHI,但需法律确认)。列为 launch 前法律咨询项。

## Premises(已确认)

- **P1 — 用户是家长,宝宝是上下文。** SOS 冷静模式是一等公民(因此排在交付计划第 1 阶段,与文字聊天同批上线)。竞品全在照顾宝宝的数据,没人照顾凌晨三点的家长本人(参见 Forbes 对 Bobbie 的评价「Stops At Info, Not Care」)。
- **P2 — 真正的竞品是免费的 ChatGPT。** 胜负手 = 安全分层 + 宝宝上下文 + 深夜语气,三件通用 AI 结构上不做的事。
- **P3 — 记录是聊天的副产品,不是义务。** 反 Coddle/Babio 的 tracker-first 架构:从对话被动提取事件(喂奶/睡眠/症状),零打卡义务,无「记录愧疚感」(行业留存失败的已证成因)。
- **P4 — 安全分层是核心,不是合规装饰。** 确定性规则引擎(纯代码,age-aware)+ LLM 分类器双层,宁可过度谨慎;分诊记录全量落库审计。失效方向永远朝保守侧(见「安全体系」的 fail-safe 策略)。
- **P5 — 接受 12-18 个月自然生命周期,** 靠口碑传给下一届新手父母;北极星是「困难的夜晚会回来」,不是永久 DAU。
- **P6 — 技术栈如 Constraints 所列。**
- **P7 — 愿景与边界:家庭记忆随孩子成长;孩子永远不是直接用户。** 以「孩子」为中心的时间轴数据模型,使未来「他两岁怕黑时我们怎么解决的」可回溯;但产品只面向家长。给未成年人直接使用的 AI 陪伴产品有重大监管(COPPA、州立法)与品牌风险,明确不做。
  - 与 P5 的关系:schema 投入只是命名与组织方式(children + 时间轴 vs babies),几乎零额外成本——若 P5 成立、用户如期流失,不亏;若部分用户带着幼儿回流,地基已备好。两者不矛盾。

## Approaches Considered

### Approach A: 「3am 救生索」(最小可行)
纯文字聊天 + 语音听写 + 月龄感知 + 安全分诊 + SOS 模式。S-M 工作量,风险低。缺点:创始人亲述的核心差异化(场景记忆)缺席,对 ChatGPT 优势只剩安全与语气。完整度 6/10。

### Approach B: 「有记忆的深夜陪伴」(理想架构)
A + 被动事件提取(时间轴)+ 上下文注入 + 晨间总结。M 工作量,风险中。完整兑现三层 wedge。完整度 9/10。

### Approach C: 「真·语音热线」(激进)
体验像深夜拨给夜班护士的电话:按一下开始说话,温柔的声音回答,屏幕只是字幕。原评估 L 工作量/高风险(实时语音管线)——**但创始人指出可复用 haus-companion 经验 + Vapi 托管语音管线,风险大幅下降**。完整度 7/10(单独看)。

## Recommended Approach(创始人选定)

**C 的交互层 + B 的大脑,Vapi 承担语音管线。**

### 产品形态
- **Call 模式(主):** 打开 App 一键「拨通」,Vapi Web SDK 建立语音通话,温柔的夜班护士声音实时应答,屏幕显示实时字幕。可随时静音/挂断。
- **Text 模式(随时切换):** 一键切回文字聊天(怕吵醒刚睡着的宝宝、或不想出声的场景),SSE 流式回复。同一会话跨模式连续。
- **安全升级 UI(两种模式共用):** 红旗触发时,语音明确说出升级指示,同时屏幕弹出高对比紧急卡片(拨打 911 / 儿科医生 / 护士热线,一键 tel: 链接);PARENT_CRISIS 触发时展示危机资源卡(988、产后心理热线),视觉上与医疗紧急卡明确区分。卡片推送为 best-effort:**字幕/聊天流中的升级话术本身始终包含可点击的紧急号码**,即使卡片渲染延迟或失败,用户也永远有可点的拨号入口(双保险)。
- **SOS 冷静模式(第 1 阶段交付):** 「I need a break」入口;「把宝宝放进婴儿床、离开房间是 100% 安全的」脚本 + 90 秒呼吸引导。静态页面 + 固定脚本,无语音/记忆依赖,与文字聊天同批上线并支持离线。
- **被动记忆(确认式,分模式设计):**
  - **Text 模式:** 提取候选以内联小卡确认(一次点击确认/忽略);
  - **Call 模式:** **不在通话中打断确认**——通话里静默提取为「待确认」,通话结束页和晨间总结中批量一键确认/修正。取舍理由:危机通话中任何插话式确认都是打扰;延迟确认牺牲少量即时性换取通话流畅。
  - 确认后写入以孩子为中心的事件时间轴,下次回答自动注入(「她 40 分钟前刚吃过,这次哭更可能是胀气」)。未确认的事件不注入回答。
- **晨间总结(被动式,MVP 无推送):** 夜间会话后次日首次打开 App 时展示一张回顾卡 + 一条针对性建议。明确不做 push notification(iOS PWA 推送权限与可靠性问题多,且「睡眠类产品主动打扰用户」违背品牌)——总结只在用户自然回访时出现。

### 架构(关键决策)
```
Next.js PWA ──(Vapi Web SDK 语音通话)──> Vapi Cloud ──(custom LLM)──┐
     │                                                              v
     └──(SSE 文字聊天, Bearer JWT)──────────────> FastAPI「大脑」(唯一的安全管线)
                                                    ├─ 确定性红旗规则引擎(纯代码, age-aware, <1ms)
                                                    ├─ Prompt 组装(人格/知识包/月龄段/今晚事件)
                                                    ├─ Claude API (claude-sonnet-5, streaming)
                                                    ├─ 分诊标签解析 + 剂量泄漏输出过滤
                                                    ├─ 被动事件提取(确认式)
                                                    └─ Supabase Postgres(RLS, 分诊审计全量落库)
     └──(Supabase Realtime 订阅 triage 事件)<──────────┘
```
- **一份大脑,两个传输层:** Vapi 通过 custom-LLM 指向 FastAPI 的 OpenAI 兼容端点(`/v1/chat/completions`),文字模式走原生 SSE 端点——安全**代码**只写一份。诚实的限定:两条路径的**输入质量不同**——语音路径喂进来的是 STT 转写(哭声环境可能出错,如 "fever of 104" 被转成 "fever before"),文字路径是用户原文。因此确定性规则引擎的有效性在语音模式下受转写质量制约;并行 LLM 分类器承担第二道网(它看到完整对话上下文,能从残缺转写中推断意图)。这也是 STT 质量 spike(见 Open Questions 1)是 launch gate 级问题的原因。
- **分诊标签机制(承载安全架构的核心协议,详述):**
  - **格式:** 系统提示词强制要求模型每条回复以且仅以一行前导标签开头:`<triage level="none|see_doctor|urgent|emergency|crisis" reason="<slug>"/>`,slug 取自提示词中枚举的固定列表(fever_under_3mo / breathing / dehydration / head_injury / parent_crisis / med_dosing_refusal / general 等)。`level="none"` 也必须输出——**标签缺失本身即为可检测的异常**。
  - **解析:** FastAPI 流式转发层缓冲首个 chunk 直到读到 `/>`(上限 120 字符),正则 `^\s*<triage level="(\w+)" reason="([\w-]+)"\s*/>` 提取并剥离,其余 token 原样透传给 Vapi(语音)或 SSE(文字)。TTS 永远读不到标签。
  - **异常策略(fail-safe 方向):** 标签缺失/畸形 → 记 malformed 事件告警、按 `none` 渲染但**该回复过输出过滤器加严档**;若同回合确定性规则引擎已命中红旗 → 以规则结果为准直接升级(代码优先于模型)。**三个信号源(确定性规则 / Haiku 分类器 / 模型分诊标签)的结果永远取最严重者。**
  - **可靠性保障:** 提示词中协议出现两次(开头+结尾);评测集含格式类用例(每条回复标签可解析);malformed 率进监控。
- **安全体系三层与 fail-safe 总策略(P4):**
  1. 确定性规则引擎(穷尽测试表,age-aware 关键词/模式,跑在用户输入上,不依赖任何模型);
  2. 并行 LLM 分类器(Haiku,2s 超时,失败静默降级);
  3. Prompt 内规则 + 输出过滤(禁剂量数字、禁劝阻就医、禁违反安全睡眠 ABC 的正则/模式扫描)。
  - **多层同时失效时的明确策略:** 规则无命中 + 分类器超时/出错 → 回复在 prompt 层守护下照常给出,但 (a) 该消息落库标记 `degraded_safety=true` 供人工复查;(b) 若用户输入弱命中高危词族(如出现 fever/breathing/fall 等词但未满足完整规则),宁可误报,自动附加 see_doctor 级提示条。**失效方向永远是过度升级,绝不静默放行。**
- **Realtime 卡片时序:** 分诊卡经 Supabase Realtime 推送为 best-effort(典型 <200ms,可能抖动);兜底是升级话术文本内嵌可点拨号号码(见产品形态)。卡片先于语音到达的场景可接受(红卡 + 随后的语音解释,方向安全)。
- **数据模型以孩子为中心:** `children`(非 babies)+ `events` 时间轴(feeding/sleep/symptom/note,来源=对话提取或手动,含 confirmed 标志),支撑 P7 的长期回溯愿景,今天就定 schema 免未来迁移。
- **知识包(定义):** `backend/app/ai/prompts/knowledge/` 下每主题一个 markdown 文件(soothing/safe_sleep/feeding/fever/colic/teething/sleep_regression/diaper_skin/development/night_survival,各 150-400 token):固定阈值数字(AAP 版本锁定)+ 各月龄段「先试这个」序列 + 该主题红旗清单。构建时全量编译进系统提示词静态块(带 prompt cache 断点,动态的宝宝上下文在断点之后)。Git 版本化,内容哈希入评测记录,**临床审核以文件版本为单位签字**。不用 RAG:全部内容 ~4-6k token,放得进提示词,检索失败在这个产品里是安全事故而非体验问题。
- 认证:Supabase Auth(magic link + Google),FastAPI 用 JWKS 验签;DB 走 SQLAlchemy+asyncpg,每请求 `SET LOCAL ROLE authenticated` + 注入 JWT claims,让 RLS 在后端路径同样生效。
- **语音延迟预算(目标 p50 ≤ 1.8s 用户停顿→首音):** STT 尾部识别 ~300ms + Vapi→FastAPI 网络 ~50ms + 规则引擎 <1ms + Claude 首 token ~400-800ms(thinking disabled、短系统提示动态块、prompt cache 命中)+ 流式 TTS 首音 ~200-300ms + 回传 ~50ms ≈ 1.0-1.5s,留 300ms 余量。缓解手段:Vapi 流式 TTS(逐句合成)、FastAPI 与 Vapi region 同区、`max_tokens≈700`、静态提示词块缓存。**若 spike 实测 p50 > 2.5s,降级策略见 Open Questions 1。**

### 分阶段交付
| 阶段 | 内容 | 验证目标 |
|---|---|---|
| 0. 地基 | Monorepo 脚手架、Supabase schema(children/events/conversations/messages/safety_events + RLS)、auth 全链路 | 登录→建档跑通 |
| 1. 大脑 + SOS(先文字) | FastAPI 安全管线(三层+分诊标签协议)+ prompt/知识包 + SSE 文字聊天 + 分诊卡片 + **SOS 冷静模式** + 黄金测试集 | 安全行为可测可信;伴侣可开始真实深夜内测 |
| 2. 语音 | **前置 spike:iPhone Safari PWA + Vapi 通话(延迟/打断/哭声环境 STT)** → Vapi assistant 配置 + custom-LLM 端点 + Web SDK 通话 UI + 字幕 + Realtime 分诊推送(复用 haus-companion 经验) | 通话延迟与转写质量达标 |
| 3. 记忆 | 确认式事件提取(分模式)+ 时间轴 + 上下文注入 + 晨间总结 | 「知道今晚发生了什么」体验成立 |
| 4a. 上线门槛(硬性) | 临床审核签字(分诊表+知识包)、真机测试(iPhone Safari + Android Chrome)、PWA 离线紧急卡、数据删除机制 | 全部通过才可上线 |
| 4b. 打磨(非阻塞) | 暗夜/红光主题、动效、空态、文案 | 体验加分项 |

阶段 1 完成即有可给伴侣使用的内测版;阶段 2 完成即兑现「热线」定位。

### Voice 风险契约(spike 失败时的回退)
阶段 2 的前置 spike 若证明 iOS Safari PWA 无法可靠支撑 Vapi 通话(WebRTC 在 standalone 模式的历史坑:媒体权限、后台挂起),回退路径按序:
1. **浏览器内运行(非 standalone PWA)** ——牺牲「安装」体验保通话;
2. **Vapi 电话线路** ——给用户一个真实电话号码,深夜直接拨打(Vapi 原生支持 PSTN;「拨打热线」的心智甚至更强,且完全绕开浏览器限制)。身份映射:注册时绑定手机号,来电 caller ID 关联账号与孩子上下文;未识别号码得到通用安全回复 + 注册引导;
3. **回退到 Approach B(文字为主 + 语音听写)** ——产品叙事从「热线」调整为「深夜陪伴」,大脑层零改动。
三条回退全部复用同一个 FastAPI 大脑——**架构上语音是可替换的传输层,这是本设计最重要的抗风险属性。**

## Open Questions

1. **哭声环境下的 STT 质量(升级为 launch-gate 级):** 主场景就是「家长压低声音说话 + 背景婴儿啼哭」——这是 STT 的对抗性环境。阶段 2 spike 必测:Vapi 降噪配置、押到什么置信度自动建议切文字、push-to-talk 是否比 open-mic 更稳。转写置信度低时的规则引擎兜底(低置信转写仍跑红旗关键词扫描,宁可误报)。
2. **Vapi 成本模型:** 按分钟计费(约 $0.05-0.15/min 含供应商),深夜长对话的单位经济性需要在内测期测量;超量时的降级策略(切文字)。
3. **语言:** 首发英文还是中英双语?创始人双语,妈妈群渠道可能偏中文社群——影响知识包审核成本(每种语言的安全话术都需临床复核)。
4. **临床审核资源:** 去哪里找儿科医生/IBCLC 审核分诊表与知识包?(护士朋友?付费顾问?)——建议阶段 1 就开始找,是 4a 的硬依赖。
